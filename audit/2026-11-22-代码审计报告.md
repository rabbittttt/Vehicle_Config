## 问题详情

### M1（中）事件历史无界增长，state 接口返回全部历史

**位置**：`catalog.py:108`（`get()` 返回全部事件）、`catalog.py:135`（每次保存/发布插入全量数据 JSON 事件）；`shared_rules.py:267`、`shared_rules.py:276`（规则侧同样模式）。

**现象**：每次「保存草稿」「发布」都会向 `events` / `rules` 库的 `events` 表插入一条包含**全量数据集 JSON** 的记录，且没有任何裁剪、归档或分页机制；`/api/state` 与 `/api/rules/state` 每次轮询都返回全部事件的 id/kind/actor/time 列表；`Store.project()` 在每次保存时还要遍历事件表补齐历史 JSON 文件。

**影响**：多人长期使用后，数据库文件、state 响应体积、`project()` 导出耗时都随操作次数线性膨胀，前端历史列表和保存耗时逐渐变慢；磁盘无上限增长。

**建议**：
1. 历史列表限量返回（如最近 100 条）+ 按页加载更早记录；
2. 事件只存 diff（`changes` 已有），全量快照仅定期或按需写入；
3. 提供历史归档/压缩机制（如超过 N 条后转存 `history/` 归档文件）。

### M2（中）`--require-proxy-identity` 参数与实际生效条件错位

**位置**：`server.py:115`（参数定义）、`server.py:123-124`（仅校验环境变量存在）、`server.py:134`（`make_server` 只接收 `secret`，不接收该参数）。

**现象**：`--require-proxy-identity` 只在启动时做"环境变量是否配置"的检查，**不会传入 `make_server`**。代理身份模式是否启用完全由环境变量 `VEHICLE_CONFIG_PROXY_SECRET` 是否存在决定：只设环境变量、漏传参数时，服务会静默进入代理身份模式（所有无代理头请求 403）；只传参数、缺环境变量时报错。

**影响**：与 README"正式多人部署必须启用 `--require-proxy-identity` 和 `VEHICLE_CONFIG_PROXY_SECRET`"的口径不一致，排障时容易误导（服务"莫名"全 403）。方向上是故障安全（不会因此变不安全），但行为不可预期。

**建议**：把 `a.require_proxy_identity` 显式传入 `make_server` 并以其作为启用开关，环境变量仅作为密钥来源；两个条件都满足才进入代理身份模式。

### M3（中）发布包硬编码文件清单

**位置**：`scripts/build_release.py:6`。

**现象**：`names` 列表手工枚举了 5 个 py 模块和 web 资源。当前清单是完整的，但将来新增 `.py` 模块或 `web/` 资源时不会自动进入发布包——本地开发正常，发布版运行时才崩溃。清单也不会发现"源码重命名后清单残留旧名"这类问题。

**建议**：改为自动枚举（根目录 `*.py` + `web/` 目录 + 固定的 README/启动脚本），断言关键入口（`server.py`、`web/index.html`）在清单内；或在构建时与 `git ls-files` 对账，出现未打包的源码文件即告警。

### L1（低）CSP 缺 `frame-ancestors`，任意站点可 iframe 嵌入

**位置**：`server.py:18`。

**现象**：CSP 已禁 inline script/style，但未设置 `frame-ancestors`，任何第三方页面都可以 iframe 嵌入本应用（点击劫持面）。注意**不能直接设 `'none'`**——门户就是通过 iframe 嵌入本应用的（`tests/portal_browser.py:6`），会破坏门户。

**建议**：按 `--public-origin` 动态生成 `frame-ancestors 'self' <公共来源列表>`；本地开发默认 `'self'`。

### L2（低）`/healthz` 在 Host 校验之后

**位置**：`server.py:38-40`（`do_GET` 中 `check_host()` 先于 healthz 分支执行）。

**现象**：健康接口虽不需要身份（`actor()` 在其后），但仍要求 Host 头在白名单内。监控系统若以未配置的内部 DNS 名作 Host 探活，会收到 403。

**建议**：把 healthz 分支移到 `check_host()` 之前（仍保持轻量只读），或在部署模板中明确健康检查必须使用配置过的公共来源 Host。

### L3（低）导入全局校验错误按"编号子串"归因

**位置**：`excel_io.py:316`。

**现象**：导入预览最后跑 `validate(result)`，错误用 `ident in message` 子串匹配归属到某个文件——只要编号恰好出现在错误文本里（如编号 `m1` 出现在任意消息中），就会误归属；纯文本错误（如「配置适用关系重复」）则落到「当前草稿」。

**影响**：仅影响预览里「文件/工作表/行号」列的显示准确性，不影响数据正确性。

**建议**：让 `validate()` 返回结构化错误（表 + 编号），或按消息的「编号：」前缀解析后精确匹配。

### L4（低）规则备份目录无清理策略

**位置**：`shared_rules.py:315-317`。

**现象**：每次发布都在 `rules/backups/` 新增一个全量备份文件，永不清理。风险低，但长期累积。

**建议**：发布成功后保留最近 N 份（如 50 份）或按时间清理。

### L5（低）服务端允许"无变更发布"（车型配置侧）

**位置**：`catalog.py:122-136`（`save(publish=True)` 无空变更拦截）；前端在 `web/app.js:297` 用 `!result.changes.length` 拦截了确认按钮。规则侧已有对应拦截（`shared_rules.py:314`「没有需要发布的规则变更」）。

**现象**：直接 POST `/api/publish` 可以发布与已发布版本完全相同的数据，推进 revision 并写一条无意义事件。

**建议**：服务端在 publish 且 `changes` 为空时返回 400，与规则侧口径对齐。

### L6（低）每次轮询都重新读取并解析 shared_config.py

**位置**：`shared_rules.py:234-241`（`_source()` 读盘 + `parse_source`）、`shared_rules.py:262-268`（`get()` 每次调用 `_source()`）。

**现象**：`/api/rules/state`（前端切到规则页即轮询/调用）每次都完整读盘 + `tokenize`/`ast.parse`/`compile` 源文件；`shared_config.py` 增长到数千行后，每个打开页面的浏览器都会周期性触发解析，CPU 浪费明显。

**建议**：基于 `(mtime, size)` 缓存解析结果，文件未变化时直接复用；发布/重载路径保持现有强制重读语义。

### L7（低）前端每次编辑全量 JSON 序列化

**位置**：`web/app.js:66-71`（`mutate()` 对整个 data 做两次 stringify）、`web/rules.js:65-75`（`change()` 同样）。

**现象**：矩阵逐格点击、逐字输入都会触发全量序列化 + 撤销栈压栈（上限 20 条 / 8MB，策略正确）。当前数据规模（每页 40 行）没问题；数据到数千行时会开始卡顿。

**建议**：保持现状但记录规模上限；若将来变慢，对矩阵单格编辑做局部变更路径。

### L8（低）`/api/import` 旧单文件接口未做 revision 校验且前端已不使用

**位置**：`server.py:76-78`。

**现象**：与 `/api/import-batch` 行为不一致（后者有 revision 校验，`server.py:94-98`）。该接口是预览专用，本身无直接危害（应用内容仍走 save 的 revision 冲突检查），但属于双入口漂移，前端已只用 `import-batch`。

**建议**：删除该接口，或补齐与 batch 一致的 revision 校验。

### I1（提示）死代码 / 仅为测试保留的导出

- `shared_rules.py:31` `LIST_FIELDS` 定义后未被引用（`rules_excel.py` 里的同名常量是在用的，勿混淆）。
- `catalog.py:138` `merge()` 生产路径未使用，仅 `tests/test_catalog.py:28` 使用。
- `server.py:5` `read_excel` 导入后未在服务端调用，只为测试再导出（`tests/test_catalog.py:4`）。

建议加注释说明"测试兼容导出"用途，或把测试改为直接从源模块导入并移除死代码。

### I2（提示）有未完成发布事务时「从脚本重新载入」会静默清空 journal

**位置**：`shared_rules.py:329-341`（`reload()` 不经过 `_ready()`，直接 `DELETE FROM journal`）、`web/rules.js:229-237`（弹窗文案只说"替换规则草稿和当前脚本基线"）。

**现象**：这是刻意的逃生门设计（`_recover()` 三分支之外的人工出口），语义合理；但当存在未完成发布事务时，重载会丢弃该事务的待发布变更，UI 弹窗并未提示这一后果。

**建议**：`reload` 检测到 pending 事务时在返回或弹窗中附加"将放弃未完成的发布事务"提示。

### I3（提示）请求处理线程无并发上限

**位置**：`server.py:108`（`ThreadingHTTPServer`，每请求一线程，无限流、无读超时）。

**现象**：内网工具 + 仅回环监听 + 门户前置时可接受。如需加固可设置 `request_queue_size`、加信号量限并发、或给 `rfile.read` 设超时。
